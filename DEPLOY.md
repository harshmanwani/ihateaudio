# Deploying

Static output served by Cloudflare Workers, with one small Worker and one R2
bucket for the single file that cannot be a static asset.

Cloudflare rather than Vercel for one reason: static bandwidth here is unmetered
and R2 egress is free. The ffmpeg core is 31 MB, and on a metered host that one
file would cost more every month the site succeeds. Vercel includes 100 GB on
Hobby and 1 TB on Pro, which is roughly 3,000 and 32,000 downloads of that file
respectively.

## What you have to do by hand

Four things left. The analytics ids and the domain are already done; what
remains is the Workers project and its R2 bucket, Search Console, and mail for
the support address.

### 1. Cloudflare Workers project

Workers, not Pages. `wrangler.jsonc` in the repo carries the whole
configuration, so the dashboard only needs:

| Setting | Value |
|---|---|
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy` |
| Version command | `npx wrangler versions upload` |
| Root directory | `/` |
| Production branch | `main` |

**Add `NODE_VERSION` = `22` under Variables and secrets.** `package.json`
requires `>=22.12.0` and the build image does not default to it.

The build no longer needs a browser. The app icons, launch images and the 42
social cards are committed, because generating them drives headless Chromium and
the build container has no Playwright browsers installed. Regenerate them
locally with `npm run assets` when the logo or the tool registry changes.

### 1a. R2, for the ffmpeg core

The one thing that cannot be a static asset. Cloudflare caps a single asset at
25 MiB and the core is 30.7 MB, so it lives in R2 and `worker/index.ts` serves it
back under the same `/ffmpeg/` path the browser already expects. R2 egress is
free, which for a 31 MB file downloaded by this many people is the reason to be
on Cloudflare at all.

```bash
npx wrangler r2 bucket create ihateaudio-ffmpeg
npm run ffmpeg:upload
```

The bucket name has to match `r2_buckets[0].bucket_name` in `wrangler.jsonc`.
Only re-run the upload when `@ffmpeg/core` changes version: the object key
carries the version, so old keys stay valid for anyone holding a cached page, and
the response is marked immutable for a year rather than the one day a stable
filename allowed.

`public/.assetsignore` is what keeps the core out of the asset upload. It is
generated by `scripts/sync-ffmpeg-core.mjs`, so it cannot be forgotten.

To check it locally before deploying:

```bash
npm run ffmpeg:upload -- --local
npm run dev:worker
```

That runs the real Worker against a local R2 simulation, which is the only way to
exercise the CSP, the headers and the R2 path together. `astro dev` applies none
of them.

The simulation lives in `.wrangler/`, which is gitignored and disposable. A fresh
clone has no local R2 at all — the `-- --local` upload above is what creates it,
reading the `public/ffmpeg/` that `npm install` regenerates, so the core round
trips from a clean checkout with no manual step. It was tracked in git until
2026-08-09, which achieved nothing except reporting a 30 MB delete-and-add of the
core every time anyone ran the Worker locally, because each put writes a new
timestamped blob filename.

Worth knowing before clearing it by hand. The blobs live per bucket under
`.wrangler/state/v3/r2/<bucket>/blobs/`, but the object metadata that gives them
their keys sits apart from them, one sqlite database per bucket under the shared
`.wrangler/state/v3/r2/miniflare-R2BucketObject/`, named by a hash rather than by
bucket. So deleting that one directory clears the keys for the models as well as
the core, leaving both sets of blobs on disk and unreachable, and
`npm run models:upload -- --local` has to be re-run. That upload is not
reproducible from a clean clone the way the core is: it mirrors
`public/models/<version>/`, which is gitignored and fetched by hand rather than
generated by a script — see 1b for where from.

### 1b. R2, for the AI models

The same problem as the core, several times over: the separation network is
64 MB and Whisper's tree is 42 MB, against Cloudflare's 25 MiB cap on a single
static asset. They sit in their own bucket rather than beside the core because
the lifecycles differ — the core moves when `@ffmpeg/core` is upgraded, the
models only when a better one is worth making everyone download again.

```bash
npx wrangler r2 bucket create ihateaudio-models
npm run models:upload
```

The bucket name has to match the `MODELS` binding in `wrangler.jsonc`, which
`scripts/upload-models.mjs` reads rather than repeating. `worker/index.ts` then
serves everything under `/models/` from it, immutable for a year, because the
version is in the path.

**The models are not in the repository.** `public/models/` is gitignored: 219 MB
of weights that change perhaps once a year has no business in git. Unlike
`public/ffmpeg/`, nothing regenerates it from `node_modules` either, so fetching
them by hand is a step a fresh clone cannot skip. The directory beneath it is
`MODELS_VERSION` from `src/lib/ai/models.ts`, currently `v1`.

**The five separation models** are MDX-Net ONNX exports from the Ultimate Vocal
Remover model repo, all in one GitHub release — `TRvlvr/model_repo`, tag
`all_public_uvr_models`:

| `public/models/v1/` | Release asset |
|---|---|
| `inst-hq3.onnx` | `UVR-MDX-NET-Inst_HQ_3.onnx` |
| `kuielab-vocals.onnx` | `kuielab_a_vocals.onnx` |
| `kuielab-drums.onnx` | `kuielab_a_drums.onnx` |
| `kuielab-bass.onnx` | `kuielab_a_bass.onnx` |
| `kuielab-other.onnx` | `kuielab_a_other.onnx` |

Two things there are easy to get wrong. They are **renamed on the way in**, so
the asset name is never the filename the code asks for. And **the size does not
tell you which model you have**: every export in the Inst family is exactly
66,759,214 bytes and most of the kuielab set exactly 29,703,204, so `Inst_HQ_1`,
`Inst_HQ_3` and `Kim_Vocal_2` are indistinguishable by size, as are
`kuielab_a_bass` and `kuielab_b_bass`. The SHA-256 in `src/lib/ai/models.ts` is
the only thing that identifies them, which is also why `src/lib/ai/store.ts`
checks it in the browser before the bytes reach ONNX Runtime.

**Whisper** is `Xenova/whisper-tiny.en` on Hugging Face — the transformers.js
conversion of `openai/whisper-tiny.en`, in the layout transformers.js expects.
Thirteen of that repo's 45 files: the eleven metadata files at its root, and
exactly two of its 31 ONNX variants, `onnx/encoder_model_quantized.onnx` and
`onnx/decoder_model_merged_quantized.onnx`. That quantized pair is what the
39 MB in the README refers to.

All of it, from a clean checkout:

```bash
V=public/models/v1
U=https://github.com/TRvlvr/model_repo/releases/download/all_public_uvr_models
H=https://huggingface.co/Xenova/whisper-tiny.en/resolve/main
mkdir -p "$V/whisper-tiny-en/onnx"

curl -Lo "$V/inst-hq3.onnx"       "$U/UVR-MDX-NET-Inst_HQ_3.onnx"
curl -Lo "$V/kuielab-vocals.onnx" "$U/kuielab_a_vocals.onnx"
curl -Lo "$V/kuielab-drums.onnx"  "$U/kuielab_a_drums.onnx"
curl -Lo "$V/kuielab-bass.onnx"   "$U/kuielab_a_bass.onnx"
curl -Lo "$V/kuielab-other.onnx"  "$U/kuielab_a_other.onnx"

for f in config.json generation_config.json preprocessor_config.json \
         tokenizer.json tokenizer_config.json special_tokens_map.json \
         added_tokens.json vocab.json merges.txt normalizer.json \
         quantize_config.json; do
  curl -Lo "$V/whisper-tiny-en/$f" "$H/$f"
done
for f in encoder_model_quantized.onnx decoder_model_merged_quantized.onnx; do
  curl -Lo "$V/whisper-tiny-en/onnx/$f" "$H/onnx/$f"
done
```

Confirm you got the models you meant before uploading them:

```bash
shasum -a 256 public/models/v1/*.onnx | while read h f; do
  grep -q "$h" src/lib/ai/models.ts && echo "ok    $(basename "$f")" || echo "WRONG $(basename "$f")"
done
```

Five `ok` lines. Nothing in the Whisper tree is checksummed anywhere —
transformers.js fetches it by name — so the test for that half is that the
transcriber runs.

To exercise the whole path locally before deploying, as with the core:

```bash
npm run models:upload -- --local
npm run dev:worker
```

### 2. Domain

The domain is on Cloudflare already. Add `ihateaudio.com` and
`www.ihateaudio.com` as custom domains on the Worker, then pick one as
canonical. Everything in the code assumes the apex (`https://ihateaudio.com`),
which is what `src/consts.ts` sets and what the sitemap and every canonical tag
emit. Redirect www to apex with a Bulk Redirect or a Page Rule.

### 3. Environment variables

**Already done.** `.env.production` in the repo carries them, and `astro build`
applies it:

| Variable | Value |
|---|---|
| `PUBLIC_GA_ID` | `G-1S7X0WG2YT` |
| `PUBLIC_POSTHOG_KEY` | `phc_sx8LvUW69VfSwPoNwo8UbG2paXmsCWmVhFLmTuGHYdib` |
| `PUBLIC_POSTHOG_HOST` | `https://a.tenmiracle.com` |
| `PUBLIC_GOOGLE_VERIFICATION` | empty, see below |

Both ids are public by design. A GA4 measurement id and a PostHog project key
appear in the page source of every site that uses them, so they belong in the
repo where a change is visible in a diff, rather than in a dashboard where it is
not. Anything genuinely secret would go in Cloudflare's environment variables,
which override the file if you ever set the same name there.

The file is `.env.production`, not `.env`, so `astro dev` never loads it and
local browsing stays out of the production numbers.

The Playwright suite is the exception worth knowing about: it builds in
production mode, so it *does* load the file. `playwright.config.ts` blanks the
three ids in its webServer environment because an empty environment value beats a
dotenv file. Without that, every test run sent a few hundred localhost page views
to production, which is exactly what happened before the
`nothing third-party loads` test caught it.

**The one still to fill in** is `PUBLIC_GOOGLE_VERIFICATION`, from Search
Console's HTML-tag method. Paste just the `content` value. Until it is set, no
verification tag is emitted at all rather than an empty broken one.

### 4. PostHog proxy

The key is a separate project from CapCut GPT, so the two products' funnels stay
apart. One thing to confirm on the first deploy: load
`https://a.tenmiracle.com/static/array.js` in a browser. A JavaScript file means
the proxy serves this project; a 404 or an error page means it needs adding for
it, because a PostHog managed reverse proxy is configured per project rather than
per organisation.

If it turns out not to be available, set `PUBLIC_POSTHOG_HOST` to
`https://us.i.posthog.com` to ship, and fix the proxy afterwards. Going direct
costs you roughly a third of your events to blockers, which is worth knowing
rather than guessing about.

### 5. Google, beyond Analytics

- **Search Console** is the one that matters, more than GA. Verify the property,
  submit `https://ihateaudio.com/sitemap.xml`, then leave it alone for a month.
  Query data is what turns the next six months of tool choices into evidence.
  Verify the **Domain** property (a DNS TXT record) rather than the URL prefix,
  so it covers www and http without a second property.
- **Bing Webmaster Tools** takes about a minute and imports straight from Search
  Console. It also feeds Copilot, which is worth having given how much of the
  SEO work here is aimed at assistants.
- **Google Analytics**: after creating the stream, turn off Google Signals under
  Admin, Data collection. The site already sends
  `allow_google_signals: false` on every page, but the property-level switch is
  the one that actually governs retention.
- **Skip Google Tag Manager.** It is a second script, a second point of failure
  and a second consent problem, to manage two tags that are already in the repo.
  Add it the day a marketing person needs to add tags without a deploy.

### 6. Email

`support@ihateaudio.com` is in the footer and on every page's contact line, so
it has to receive mail before launch. Cloudflare Email Routing does this free:
Email, Email Routing, add `support@` as a custom address forwarding to your real
inbox. It needs the MX records Cloudflare offers to add for you.

## Already handled in the repo

- **`public/_headers`** carries the CSP, the cache policy per asset class, and
  the CORS headers on `/llms.txt` and `/tools.json` that let assistants read
  them. The CSP allowlists exactly `googletagmanager.com` and
  `a.tenmiracle.com` and nothing else.
- **`public/robots.txt`** names 18 AI crawlers as allowed and points at the
  sitemap.
- **`public/sw.js`** caches the shell and the tool art for offline use, and
  deliberately never caches the 31 MB ffmpeg core.
- **`public/manifest.webmanifest`** plus generated icons, maskable icon, 11 iOS
  launch images and 2 install-dialog screenshots.

## Verifying a deploy

```bash
npm run build && npm run seo
```

Expect **44 pages, 0 errors, 0 warnings**. Then:

```bash
npm test && npx playwright test
```

Expect **125 unit** and **285 end-to-end**. There is also a run against real
files, which is the one that catches what synthetic tones cannot:

```bash
npm run dev
npm run verify -- ~/path/track.mp3 ~/path/second.mp3
```

Expect **38 passed, 1 skipped**. The skip is the voice recorder, which needs a
live microphone.

After the first production deploy, check by hand:

1. `curl -sI https://ihateaudio.com | grep -i content-security` returns the
   policy. If it does not, `_headers` did not ship, and the analytics scripts
   will be silently blocked in some browsers.
2. Open a tool page with the network tab filtered to `a.tenmiracle.com`. One
   request to `/static/array.js` and one to `/i/v0/e/` per event.
3. GA4 Realtime shows the visit.
4. Chrome's install button appears in the address bar. If not, open Application,
   Manifest in devtools: it names the exact field that failed.
5. Load a tool page, turn off the wifi, reload. It should still work. That is the
   service worker, and it is the claim the whole product rests on.
6. `curl -sI https://ihateaudio.com/vocal-remover | grep -i cross-origin` returns
   both the opener and embedder policies. If it does not, the AI tools still
   work and are about 3.5× slower than they need to be, which is the kind of
   regression nothing else will report. Confirm it took effect rather than just
   shipped by running `crossOriginIsolated` in the console on that page.

## A note on the AI tools

Both things the model-backed tools needed are now configured:

- The weights are in R2 alongside the ffmpeg core, served by the same Worker.
  That keeps the privacy claim intact and R2 egress is free. The alternative was
  extending `connect-src` to
  `https://huggingface.co https://cdn-lfs.hf.co https://cdn-lfs-us-1.hf.co`,
  which is less work and puts a third party in the request path.
- `Cross-Origin-Opener-Policy: same-origin` and
  `Cross-Origin-Embedder-Policy: require-corp` on the six AI routes, which is
  what gets ONNX Runtime its four threads. Deliberately not on `/*`: nothing
  else on the site benefits, and require-corp would then have to be defended on
  every page forever. As it turns out both analytics scripts do satisfy it —
  googletagmanager.com sends `Cross-Origin-Resource-Policy: cross-origin` and
  posthog-js sets `crossorigin="anonymous"` on every script it injects — but
  that is their arrangement to change rather than ours.

The part of that which is easy to get wrong: **a require-corp document may only
create a dedicated worker whose own response also says require-corp.** Same
origin is not sufficient. So `/_astro/*` and `/workers/*` carry the header too,
covering the separation worker, ffmpeg's worker and Whisper's. Without it the AI
tools accept a file and then hang on "Starting the engine" while the console
reports `ERR_BLOCKED_BY_RESPONSE` against a script that is plainly being served.
Because those filenames are content-hashed and `_headers` has no mid-path
wildcard — `/_astro/*worker*` matches nothing — the header goes on the whole
prefix. That is harmless: COEP is only read when a response becomes a document
or a worker global.
